# Shell integration for `gig cd` via a stderr-drawn picker, not a PTY wrapper

`gig cd` needs to change its *parent shell's* working directory, which a subprocess can never do on its own - some shell-side glue has to read a result back out of `gig` and `cd` with it. The complicating factor is that the same invocation is also interactive: it draws a fuzzy-picker UI.

`gig` avoids that problem instead of working around it: `dialoguer`'s `FuzzySelect` supports `interact_on(&Term)`, so the picker is drawn on `Term::stderr()` while stdout is reserved for exactly one thing - the chosen repo's absolute path on success, nothing at all on cancel/error. `gig shellenv`'s function is then a plain `dir=$(command gig "$@") && cd "$dir"` - no PTY, no log file, no marker-line parsing, and it only special-cases the `cd` subcommand rather than wrapping every `gig` invocation. `gig cd` also stays independently useful without the shell function installed at all (`cd "$(gig cd)"`), since the stdout contract is the same either way.

**Consequence:** this depends on `dialoguer` accepting an explicit output `Term` for its prompts - if a future prompt type or picker replacement doesn't support that, the PTY-wrapper approach becomes necessary again. `gig cd` proactively checks `Term::stderr().is_term()` and fails with a clear message rather than letting `dialoguer` fail more obscurely when stderr isn't a real terminal (piped, CI, etc.) - there is no way to exercise the genuinely interactive path in this repo's CLI-level (`assert_cmd`) test harness, since it never allocates a PTY either; only the non-interactive failure paths are covered by automated tests.
