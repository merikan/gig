# A sidecar file, not stdout, hands `get`'s destination back for auto-cd

`gig get` gained auto-cd: on success (freshly cloned or already-cloned, with or without `--pull`), `gig shellenv`'s wrapper function should `cd` into the destination, controlled by `gig.autocd-into` (default enabled) and overridable per-invocation with `--cd`/`--no-cd`. `gig cd` already solves the "a subprocess can't change its parent shell's directory" problem via `gig shellenv`: it draws its picker on stderr and prints only the chosen path to stdout, so the wrapper function does `dir=$(command gig cd) && cd "$dir"` (ADR 0005). `get` can't reuse that trick: `git clone`/`git pull` inherit stdio directly (ADR 0001) precisely so their own live output (clone progress, `--pull`'s diffstat summary) streams straight to the user - and that diffstat lands on the same stdout stream a `dir=$(command gig get ...)` capture would need to reserve for the destination path alone. Capturing it would silently swallow git's own pull output instead of showing it live, regressing ADR 0001 for exactly the case (`--pull`) it was written for.

Instead, `gig shellenv`'s wrapper sets an environment variable, `GIG_CD_FILE`, to a fresh `mktemp` file before every `command gig "$@"` call - unconditionally, not just for `get` - and reads it back afterwards. `get` writes its resolved destination to that file itself, directly (not via stdout/stderr), only when `GIG_CD_FILE` is set and auto-cd applies (`--cd`, or no `--no-cd` and `gig.autocd-into` isn't `false`); every other subcommand ignores the variable entirely. stdout and stderr stay fully inherited throughout, so git's own output is untouched. The wrapper `cd`s only when `command gig` exited zero and the file is non-empty, then removes the tmp file either way.

**Consequence:** this is a second, different shell-integration mechanism alongside ADR 0005's stdout-only one for `cd` - deliberately not unified, since `cd`'s stdout-only contract still works fine and changing it would be unrelated scope. `get` without the wrapper eval'd is completely unaffected: `GIG_CD_FILE` is simply absent, so `maybe_write_cd_file` is a no-op and `get` behaves exactly as before - its own human-readable "Cloned into `<path>`"/"Already cloned at `<path>`" messages remain the only way to see the destination, same as always. A write failure (tmp dir vanished, permission denied) is non-fatal: `get` has already finished the clone/pull it was asked to do by the time it writes the sidecar file, so a failure there is reported as a warning on stderr rather than failing the whole invocation - the same reasoning ADR 0001 already applied to *not* re-quoting git's own stderr on clone/pull failure (the operation's real outcome is what matters, not this side channel).
